# DealPilot AI — Phase 2 Backend Foundation

The Phase 2 backend lays down the Node.js/Express/Mongoose foundation: config validation, logging, error taxonomy, all shared middleware, 11 domain models, database connection, app wiring, graceful shutdown, utility helpers, health endpoints, seed data, and constants. All required files are present and structurally correct. The approach is coherent — ESM throughout, Joi config validation, Winston with redaction, a clean error class hierarchy, and token handling that stores hashes rather than raw values. The main issues are a missing `unique` constraint on the `Deal` model's `userId+investorId` pair (the feature spec explicitly requires deduplication), a partial-mutation bug in the `validate` middleware, and the `authorize` middleware relying on synchronous throws caught by `express-async-errors` — which works but is fragile.

**Watch for:** Deal deduplication index absent (confirmed blocking); validate middleware mutates `req.body` before detecting param errors (confirmed); authorize throws synchronously without `next()` (likely safe but fragile).

**Verdict**: NEEDS_CHANGES

---

## High-level view

Config, logging, and error infrastructure are in good shape. Joi validation guards `MONGODB_URI` and both JWT secrets as required fields, the frozen config prevents accidental mutation, and the logger's redaction list covers all credential fields. The error handler correctly maps Mongoose-native errors to typed `AppError` subclasses and sanitizes messages in production.

Token and password handling follow the right pattern: `passwordHash`, and both `tokenHash` fields have `select: false`, bcrypt-12 is used for passwords, and SHA-256 for token storage. No raw secrets reach the logger.

The `Deal` model is missing a `unique` constraint on `{userId, investorId}`. The product spec explicitly requires preventing duplicate investor records in a pipeline. The existing index is non-unique — it serves query performance only and won't enforce the invariant at the database level.

The `validate` middleware mutates `req.body` (stripping unknown fields) during the `body` pass before knowing whether `params` will fail. The request is ultimately rejected, but the object is already partially transformed. Using a staging buffer avoids this asymmetry.

`authorize` throws synchronously instead of calling `next(err)`. This works only because `express-async-errors` is imported first in `app.js`. The `authenticate` middleware uses explicit `try/catch` + `next(err)` and `authorize` should match it.

Two lower-priority gaps: `Activity.type` has no `required: true`, so typeless activity records can be persisted; and the `Startup` model has no compound index for `{industry, stage}` or `profileCompleteness`, which will cause collection scans once matching queries run against it.

<details>
<summary>Issues (5)</summary>

1. **Deal deduplication missing** — The `Deal` model's `{userId, investorId}` index is not `unique: true`. The product spec requires preventing duplicate investor records in a pipeline. Add `{ unique: true }` to `dealSchema.index({ userId: 1, investorId: 1 }, { unique: true })`.

2. **Validate middleware partial mutation** — `validate.js` assigns `req[target] = value` (the Joi-stripped value) in the loop before determining whether all targets pass. If body passes and params fails, `req.body` is mutated but the middleware returns a validation error. Collect all transformed values in a staging object and only apply them to the request after all targets pass.

3. **Authorize throws synchronously** — `authorize.js` throws `AuthenticationError` and `ForbiddenError` directly instead of calling `next(err)`. This works only because `express-async-errors` patches Express's layer wrapper. Switch to explicit `next()` calls to make the error propagation self-contained and not dependent on import order.

4. **Activity type not enforced** — `Activity.type` is an `enum` without `required: true`, allowing typeless records to be persisted. Add `required: true` to the `type` field.

5. **Startup discovery indexes missing** — The `Startup` model has no compound index for matching queries (e.g. `{industry, stage}` or `profileCompleteness`). Add indexes to support Phase 3 investor-matching filter queries before they hit a cold collection.

</details>

<summary>Details</summary>

### Deal deduplication index absent

The product spec states: "Prevent duplicate investor records in a founder's pipeline." The `Deal` model declares:

```js
dealSchema.index({ userId: 1, investorId: 1 });
```

Without `{ unique: true }`, this is a performance index only. A founder can create two deals for the same investor. The `SavedInvestor` model gets this right — `savedInvestorSchema.index({ userId: 1, investorId: 1 }, { unique: true })` — but `Deal` does not follow the same pattern. This is a confirmed gap against a stated feature requirement.

### Validate middleware partial mutation

```js
for (const target of targets) {
  const { error, value } = schema[target].validate(req[target], { stripUnknown: true });
  if (error) { /* push to fieldErrors */ }
  else { req[target] = value; }   // ← mutation before loop ends
}
if (fieldErrors.length > 0) return next(new ValidationError(...));
```

`req.body` is replaced with the Joi-cleaned value during the `body` iteration. If `params` then fails, the middleware rejects the request but `req.body` is already in its stripped form. Today this has no consequence because the route handler never executes, but it violates the principle that a rejected middleware leaves the request unchanged. The fix is to buffer into a staging object and flush at the end.

### Authorize synchronous throw dependency

`express-async-errors` wraps Express's `Layer.prototype.handle_request` to route thrown errors to `next`. This works for both async rejections and synchronous throws, but it is an implicit dependency: if `express-async-errors` is removed or its import is moved after `app.use(authorize)`, thrown errors in `authorize` will crash the process with an unhandled exception rather than producing a 403. The `authenticate` middleware avoids this with an explicit `try/catch` + `next(err)` pattern, which is the safer approach and should be applied consistently to `authorize`.

### Seed counter bug (non-blocking)

```js
const result = await Investor.findOneAndUpdate(..., { upsert: true, new: true });
if (result) { upserted++; } else { modified++; }
```

`findOneAndUpdate` with `upsert: true` and `new: true` always returns the document — `result` is never falsy — so `modified` stays at 0 and `upserted` always equals `DEMO_INVESTORS.length`. The `console.log` summary is accurate by accident. This doesn't affect correctness, but the counter split is dead code.

### Activity model `type` not required

`Activity.type` uses `enum: ACTIVITY_TYPES` without `required: true`. An activity record can be saved with no type at all — it would pass Mongoose validation as `undefined`. Since all activity-writing paths in Phase 3 will set the type explicitly this is unlikely to cause silent corruption, but the constraint should be there to enforce it at the model layer.

### Missing startup discovery indexes

The `Startup` model has no explicit compound index beyond the `unique: true` on `userId`. The investor-matching queries in Phase 3 will filter startups by `{industry, stage}` and sort by `profileCompleteness`. Without these indexes, those queries will collection-scan as the startup count grows. The `userId` unique index handles per-user lookups; the discovery path needs its own index.
